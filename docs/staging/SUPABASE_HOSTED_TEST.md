### 3.2 SQL apply method

* **Supported method (use this):** the SQL editor (paste the whole `integrations/supabase-edge/sql/0001_idr_projection.sql`
  and run it once), or
  `psql "<DIRECT_OR_SESSION_POOLER_URL>" -v ON_ERROR_STOP=1 -f integrations/supabase-edge/sql/0001_idr_projection.sql`
  over the direct connection or the session-mode pooler. These are the two methods SETUP.md names and the local
  run used (`psql -f`).
* **Why not a migration runner.** R3-D made the script one transaction (`begin;` … `commit;`, with
  `idr_schema_version()` defined last), so a failure part-way leaves the previous version intact, even with
  `psql -f`. The Gate 3 re-review noted that a runner that wraps each file in its **own** transaction is ended
  early by the script's `commit;`: the runner's bookkeeping is then no longer atomic with the script, and this was
  not verified for `supabase db push`. A public CLI bug report (section 1) describes `COMMIT; BEGIN;` inside a
  migration file leading to statements, and later files, not being applied with only a warning. So `supabase db
  push` is **not** used for the main path.
* **E1 (optional experiment, closes the caveat):** on a second throwaway project (or after the main tests, on a
  fresh project), copy the SQL into `supabase/migrations/` and run `supabase db push`; then check
  `idr_schema_version() = 4`, that every `idr_*` function exists, and whether the CLI recorded the migration. Record
  the CLI version and the outcome for SETUP.md.
* **HU (upgrade path):** before applying the current SQL to the main project, apply the previous releases in order
  (`integrations/supabase-edge/test/fixtures/0001_idr_projection.6318ab2.sql`, then `...f12b1ad.sql`), insert a few
  synthetic rows as the owner role, run SETUP.md's "Before upgrading" queries, then apply the current SQL.

### 3.5 Scheduling: pg_cron, pg_net, Vault

* Enable `pg_cron`, `pg_net` and `supabase_vault` (Dashboard > Database > Extensions).
* Store `idr_sync_url` (`https://<PROJECT_REF>.supabase.co/functions/v1/idr-sync`) and `idr_sync_secret` (= the
  function's `IDR_SYNC_SECRET`) in Vault, then run the `cron.schedule(...)` of `sql/schedule.example.sql`
  **verbatim** (`*/5 * * * *`).
* Note: the example's `pg_net` timeout is 60 s. With `IDR_BUDGET_MS` above about 55 s (H12), `pg_net` records a
  timeout while the function keeps running and finishes; the next run continues from the stored cursor. H12
  records what hosted pg_net reports in that case.

### 3.6 Auth

* Authentication > Sign In / Providers: **"Allow new users to sign up" off**; e-mail provider with password
  sign-in on (users are created by the admin API, so no e-mail is ever sent and no SMTP is needed).
* JWT expiry: record the value; the acceptance script prints the issued tokens' lifetime. SETUP.md asks for a short
  expiry because a revoked reader keeps reading until the token expires.
* The `app_metadata.idr_reader` claim is granted only through the admin API from a trusted shell (SETUP.md step 5,
  never from a browser). The acceptance script creates two temporary users with random addresses at
  `SBH_TEST_EMAIL_DOMAIN` (default `example.test`), grants and revokes the claim, and deletes both users at the
  end, also after a failure. If hosted Auth refuses that domain, set another reserved domain and record it.

### 3.7 The resolver side

The isolated Railway development resolver (D7, mock provider). For this campaign the owner sets, and reverts at
teardown: a staging-only `REPORTING_AUTH_TOKEN`; `ALLOW_DOCUMENTATION_RANGES=true` (so that the seeding step can
create synthetic observations for RFC 5737 / RFC 3849 addresses through the mock provider; never in production);
for H10 only, `OBSERVATION_RETENTION_DAYS=1`.

## 5. Acceptance criteria

The hosted test **passes** when:

1. H1 to H8, H11 to H15 and HU have no FAIL, on the plan and region the owner intends for clients;
2. H12 shows no platform limit error at the largest configuration the adapter allows (`IDR_PAGE_LIMIT=500`,
   `IDR_BUDGET_MS=140000`), or the adapter's documented limits are lowered to what passed;
3. H4 records the Postgres version, the extension versions and the role timeouts, and SETUP.md is updated where
   they differ from the local run;
4. G4-L4 is either fixed (schema 5, H4 PASS) or its INFO result is attached to the owner's risk acceptance;
5. every temporary user, token and secret is removed or rotated at teardown (section 8).

## 8. Teardown (owner)

1. Unschedule the job (`select cron.unschedule('idr-sync');`), then **delete the project** (Settings > General).
   This removes the database, the function, its secrets, Vault, Auth users and logs.
2. On the development resolver: rotate (remove) the staging-only reporting token; set
   `ALLOW_DOCUMENTATION_RANGES` and `OBSERVATION_RETENTION_DAYS` back to their earlier values. The seeded
   synthetic observations expire with the resolver's retention buffer, or can be removed with the resolver's own
   tooling.
3. Revoke the Supabase personal access token used by the CLI if it was created for this campaign; delete the
   private env files and the downloaded CA certificate.
4. If the organisation was upgraded to Pro only for this, downgrade after the billing period; check the billing
   page one day later.
